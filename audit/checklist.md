# 점검표 v2 — household-report-update

이 파일이 점검 절차의 정본이다. 사용자는 짧은 지시만 붙여넣고 실제 절차는 이 파일을 읽어서 수행한다. 매 회차 끝에 "점검표 개정안"에서 사용자가 채택한 것만 반영한다. 커밋은 두 번 — 진단 직후 audit/last-audit.md(1차), 사용자가 개정안을 채택한 뒤 audit/checklist.md(2차). 채택을 묻기 전에 이 파일을 고치지 마라.
버전: v2 (2026-09-26 — 1회차 점검표 개정안 12건 전부 채택·반영, "되돌리면 안 되는 것" 표 갱신) · v1 (2026-09-26 — baemin·hometax 점검표를 이 스킬 구조에 맞춰 옮김)

아직 고치지 말고 진단만. 뭘 고칠지는 사용자가 고른다.

[시작 전 확인 ① — 토큰과 push 경로]
마무리에 저장소로 파일을 올려야 한다. 요청 문구에 토큰이 없으면 첫 응답에서 물어라:
> 점검을 시작하겠습니다. 마무리에 기준선과 점검표를 올려야 해서 household-report push 토큰(Contents: Read and write)이 필요합니다. 지금 주시면 진단 후 바로 올리고, 없으면 파일로만 드리겠습니다.
이 저장소는 git push가 아니라 GitHub Contents API로 올린다(scripts/deploy.py의 push()). 클라우드에서 그대로 된다. deploy.py --code-only는 CODE_GLOBS(SKILL.md·pipeline.py·build.py·scripts/·audit/·install/·tests/)를 자동 스캔해 올리지만, 점검 회차에는 코드가 바뀌지 않으니 점검 파일만 push()로 직접 올린다:
  cd /home/claude/gagyebu && python3 - <<'EOF'
  import sys; sys.path.insert(0, 'scripts'); from deploy import push
  T = '<토큰>'
  for f in ['audit/last-audit.md']:   # 2차 커밋 때 'audit/checklist.md', 'install/SKILL.md' 추가
      push(T, f, f, f'{f} 갱신')
  EOF
push()는 내용이 같은 파일을 건너뛴다("변경 없음"). 토큰은 명령줄·대화·환경변수(GITHUB_TOKEN)에만 쓰고 파일에 남기지 않는다. 채팅 보고 마지막 줄에 폐기 안내. index.html은 이 회차에 절대 올리지 않는다(배포는 점검이 아니다).
커밋 해시는 codeload tarball에 .git이 없으니 API로 조회한다(비인증은 시간당 60회 제한에 걸린다 — 1회차에서 실제로 걸렸다):
  curl -s -H "Authorization: Bearer <토큰>" "https://api.github.com/repos/LeeKwanBeom/household-report/commits?per_page=1"

[시작 전 확인 ② — 정본이 세 곳에 있다]
(a) 이 대화에 로드된 설치본 SKILL.md — 부트스트랩. 행수는 wc -l 기준으로 적는다(1회차: 49행, 파일 끝 개행 없음, md5 b411b109…). 절차·명령어·규칙이 여기 다시 들어가 있으면 그 자체가 결함이다. 얇게 유지하는 게 이 구조의 핵심이다.
(b) 저장소 install/SKILL.md — 부트스트랩 원본. 없으면 "부트스트랩 원본 부재"를 결함으로 올리고, (a)를 그대로 넣는 안을 제시한다. 있으면 (a)와 md5가 같은지 대조한다 — 다르면 어느 쪽이 최신인지 판정해 결함으로 올린다.
(c) 저장소 SKILL.md — 실제 설명서 정본. 진단은 이것과 코드를 기준으로 한다.
설치 경로는 `ls /mnt/skills/plugins/`로 실제 확인한다. (a)의 문구 속 경로와 실제가 다를 때만 결함이다(1회차 확인: 이 환경의 실제 경로는 /mnt/skills/plugins/household-report-update/ 로 문구와 같다). 고치면 사용자가 Claude 설정에서 스킬을 재업로드해야 반영된다는 점을 결과에 명시해라.
받은 저장소의 실제 파일 목록(ls -R, .git 제외)과 커밋 해시를 기준선 "점검 대상"에 적어라. 행수는 wc -l 기준으로 적고, 바이트 수는 적지 않는다.

[시작 전 확인 ③ — 실 CSV 없이는 진단이 절반이다]
사용자가 첨부한 최신 가계부 CSV로 실제 1회 실행한다: python3 pipeline.py <csv> → python3 build.py → python3 scripts/detect_ended.py <csv> → python3 -m unittest discover tests. CSV가 첨부돼 있지 않으면 **시작하지 말고 요청해라.** tests/fixtures/는 합성 데이터라 실 CSV를 대신하지 못한다.
- CSV의 날짜 min/max와 오늘과의 간격을 "점검 대상"에 적어라(예: 2026-01-01~2026-09-25, 최종일 1일 전).
- 실행 산출물(/mnt/user-data/outputs/이관범_가계부_분석_리포트.html)을 열어 실물로 확인한다. 코드만 읽고 "맞다"고 쓰지 마라.
- 조건을 만들어 보는 실험(카드명을 결제수단에 넣기, 연도가 다른 같은 월 번호 사본, 세부내용에 `};`, 이체 행 삭제 등)은 **CSV 사본**으로 한다. 원본은 건드리지 않는다.
- **실측 출력 마스킹 규칙.** pipeline·detect_ended 출력은 `sed -E 's/[0-9]{1,3}(,[0-9]{3})+/[금액]/g'`를 거쳐 표시한다. 사본 실험에서 잔고·합계 델타는 숫자 대신 "변화 있음/없음"·"부호"만 출력한다. node --check 오류 메시지는 DATA 줄 앞부분을 그대로 찍으므로 마스킹 후 표시한다. 1회차에서 이 세 경로로 실제 합계가 대화에 노출됐다.
- **배포하지 않는다.** deploy.py로 index.html을 올리지 마라. validate_html은 실행해도 된다(로컬 검증만 — 저장소 index.html이 있으면 잔고 급변 검사까지 돈다).
- pipeline.py의 ACCOUNTS_START 등 규칙 상수는 읽기만 한다. 값을 바꾸지 마라.

[공개 저장소 — 개인 재무 데이터 보호]
저장소는 Public이다. 기준선·점검표·채팅 보고에 실제 잔고·거래 내역·금액·계좌 잔액을 옮겨 적지 마라. 실험 수치는 합성값(예: "90만원 행을 넣었더니")만 쓰고, 실제 데이터에서 발견한 건은 "N건, 어느 컬럼" 수준으로만 적는다. 계좌명·카드명·규칙 항목명(코드에 이미 있는 것)은 적어도 된다. tests/fixtures/에 실 CSV 행을 복사해 넣지 않는다.

[0단계 — 기준선 대조. 신규 진단보다 이걸 먼저]
직전 기준선 파일 audit/last-audit.md를 먼저 읽어라. "결함"·"개선안"·"수정 기록" 항목마다 지금 실물에서 다시 확인해 해결됨/미해결/근거없음으로 판정하고, 판정 근거로 지금 파일의 경로+행 번호+원문을 인용해라. 요약하지 말 것. 직전 회차의 "통과" 목록도 하나씩 다시 본다(그대로 통과인지). 직전 회차가 수정 회차였으면 그 수정이 실물에 들어가 있는지(검증 회차)가 먼저다.
그다음 문서와 코드가 다른 속도로 움직인 흔적(코드만 고치고 문서가 안 따라옴 / 문서만 고침)을 양방향으로 찾고, 마지막에 기준선에 없던 신규 항목만 찾아라.
기준선은 아래 [기준선 형식]으로 쓰고, 직전 기록은 파일 아래 "이전 기록"으로 원문 보존한다.

[의도된 동작 — 결함으로 올리지 마라]
사용자가 알고 정한 것이거나 SKILL.md에 이유가 적힌 것이다. 바꾸려면 사용자 승인이 필요하다.
- 시작 잔고(ACCOUNTS_START)는 고정값이며 매 실행 때 사용자에게 묻지 않는다(2026-09-18 지시). 사용자가 먼저 "다시 쟀다"고 말할 때만 balance·as_of를 같이 갱신한다.
- 이체(구분=="이체")는 총수입·총지출에서 제외하고 잔고 계산에만 반영한다.
- 잔고는 계좌별 as_of 다음날부터의 거래만 더한다. 예외 목록은 없다.
- 가장 최신 월은 막날 데이터가 있어도 미완성으로 보고 "매달 예상 고정지출"에서 제외한다. 다른 섹션에는 포함한다. 월초에 전월 마감 CSV로 돌리면 전월이 미완성으로 잡히는 것도 규칙대로다(2026-09-26 사용자 확인).
- 종료 추정 항목은 화면에 넣지 않고 대화로만 보고한다([확인 필요]만). 종료 추정 공백은 완성월 기준이라 진행 중인 달의 결제는 반영되지 않는다 — 재개한 구독은 다음 달 CSV까지 걸릴 수 있다.
- 리모트뷰는 종료 항목이 아니다(2026-09부터 재구독). 카카오 톡서랍은 제외 대상이 아니다(SHINHAN_FIXED_ITEMS에 있음).
- 03번 카드사별 결제 내역은 날짜 오름차순. TOP 15에서 회생·가족 용돈·커플통장 제외.
- 커플통장은 화면에서 감춘다(HIDDEN_ACCOUNTS). 커플통장 잔고 음수 경고는 사용자가 신경 쓰지 않기로 했다(2026-09-26) — 대화로만 전달되고 화면에는 안 실린다.
- 완전히 같은 행은 경고만 한다(중단 아님). 같은 날 같은 금액이 실제 별건인 경우가 있다.
- 실행일보다 뒤인 날짜 행은 중단하지 않고 집계에서 빼고 경고한다(2026-09-26 지시).
- 저장소는 codeload로 받는다(raw.githubusercontent.com은 5분 캐시라 금지). 작업 디렉토리는 /home/claude/ 하위.
- 토큰은 매번 사용자에게 받고 파일에 저장하지 않는다.
- 규칙 값의 유일한 원본은 pipeline.py 상수이며 bundle로 build.py에 전달된다. 화면 문구에 숫자를 옮겨 적지 않는다.
- 리포트 화면은 GitHub Pages로 공개 배포된다(사용자 선택).

[특히 이런 걸 찾아줘]

■ A. SKILL.md ↔ 코드 괴리 (최우선)
- 7단계 절차의 명령어·옵션(--with-code, --code-only, --ack-balance, GITHUB_TOKEN)이 deploy.py와 맞는지. deploy.py CODE_GLOBS가 저장소 실제 파일을 다 덮는지(_scan_code_files() 결과와 ls 대조) — audit/·install/·tests/가 빠지면 결함, CSV·data_bundle.json이 들어가면 결함.
- "리포트 구조(14개 섹션)" 표의 번호·id·그룹이 build.py의 실제 섹션 순서·id와 맞는지(renumber_sections 결과와 대조).
- "계산 규칙"의 항목(ENDED_FIXED_ITEMS 6건, MANUALLY_EXCLUDED 1건, SUBSCRIPTION_ALIASES, TOP_EXPENSE_EXCLUSIONS, SHINHAN_FIXED_ITEMS, CARD_TARGETS, EXPECTED_MONTHLY_TRANSFERS)이 pipeline.py 상수와 일치하는지. 문서에 옮겨 적힌 숫자 리터럴이 상수와 어긋나면 결함.
- 5단계 경고 목록이 warnings_for()의 종류와 1:1인지(코드에만 있거나 문서에만 있으면 결함).
- SKILL.md 안의 시점 의존 서술이 다음 달에도 맞는 문장인지. 낡을 문장은 "언제부터 틀려지는지"를 적어라. 지난 달 예외는 "이력" 절로 갔는지.
- 설치본 부트스트랩 (a)의 명령이 지금도 그대로 동작하는지(codeload 수령 → SKILL.md·pipeline.py·build.py·scripts/ 존재).
- (조건부 — 해당 파일에 변경 커밋이 있을 때만) 인자 순서, CSV 컬럼명 9개가 EXPECTED_COLS 한 곳에서만 정의되는지.

■ B. 단일 출처가 지켜지는지
- pipeline.py 상수의 사본이 build.py·detect_ended.py·SKILL.md에 있는지(값·목록). detect_ended.py가 import하는지 실물 확인.
- build.py에 숫자·연도·월 이름을 하드코딩한 곳(docstring 제외).

■ C. 조용한 실패가 가능한 경로 (이 스킬의 최대 위험은 "조용히 틀린 리포트 배포")
- 결제수단에 카드명·빈칸이 들어간 지출 행: 경고가 뜨는지 실측(사본).
- 이체 행 누락·합계 불일치: EXPECTED_MONTHLY_TRANSFERS 경고가 뜨는지 실측. 3단계 묻기 절차가 SKILL.md에 살아 있는지.
- pipeline.py validate()가 무엇을 검사하는지 전부 나열하고, 각 검사를 깨뜨려 FAIL이 뜨는지 실측. 방법: CSV 사본으로는 재현 불가(항등식)이므로 **bundle을 메모리에서 변조해 validate()를 호출**한다. 0건 가드는 전부 0인 bundle로. 파괴 방법과 결과를 표로.
- warnings_for()의 경고 종류가 전부 tests/에 있는지, 화면 13번이 bundle["warnings"]를 렌더하는지(하드코딩 문구가 다시 생겼으면 결함).
- 결제수단 오타·공백·대소문자 변형, 비고 오타("현대 카드")가 어떤 경고를 내는지.
- 금액 파싱(parse_amount): 쉼표·원 표기·음수·빈칸·전각 숫자. 음수·0 경고가 뜨는지.
- 날짜 파싱: 형식 변형(경고), 미래 날짜(제외+경고, 최신 월 불변), as_of 이전 날짜의 이체 행(의도대로 제외).

■ D. 화면이 데이터와 맞는지 ※ 실 CSV로만 판정 가능
- 산출 HTML의 임베드 DATA(bundle)에서 계좌 잔고·월별 수입/지출·고정지출 예측·카드 실적 값을 뽑아, pandas로 CSV에서 독립 계산한 값과 대조(최소 5개 값). 값은 기준선에 적지 말고 "일치/불일치 N개"로만.
- 저장소에서 받은 index.html(직전 배포본)의 DATA·비데이터 HTML을 신규 빌드와 대조해 "저장소 코드 = 배포본을 만든 코드"인지 확인한다. 차이가 있으면 원인을 적는다(코드가 배포 뒤 바뀐 것인지, 배포가 옛 코드로 된 것인지).
- 섹션 14개가 전부 렌더되고 번호가 등장 순서대로인지, `{REF:` 치환 잔존 0인지.
- 월 라벨: **연도가 다른 같은 월 번호가 있는 사본**(11개월로도 재현됨)으로 연도 접두가 붙는지. 연도 넘김(12→1월) 경로.
- 최신 월 미완성 판정: CSV 최종일이 월말이고 다음 달 행이 0건인 사본으로 돌려 어느 달이 제외되는지 확인. 규칙대로면 결함 아님.
- sw.js·manifest.json: github.io는 이 환경 허용 도메인 밖이라 **코드 읽기까지만** 가능하다. 실측 못 함을 기준선에 적는다.

■ E. 배포 스크립트(deploy.py)

- 빈 커밋: 최근 커밋의 `commits/{sha}` stats.total == 0인 것이 있는지 API로 판정. 같은 파일을 두 번 push()하면 두 번째가 "변경 없음"으로 건너뛰는지.
- CODE_GLOBS 스캔 결과에 CSV·data_bundle.json·index.html이 없는지.
- 토큰이 환경변수 GITHUB_TOKEN으로도 받아지는지, SKILL.md가 그 방법을 안내하는지.

[결과 정리 방식]
결함은 심각도 순으로, 항목마다: 지금 틀렸는지/언제 틀려지는지 · 실측/추론 · 고치면 뭐가 달라지는지 · 작업 경로. 작업 경로는 두 종류뿐이다:
  · 저장소 파일(SKILL.md·pipeline.py·build.py·scripts/·audit/·install/·tests/) → 수정 후 deploy.py --code-only 또는 push()로 올리면 반영 끝(부트스트랩이라 재패키징 없음).
  · 설치본 부트스트랩 문구 → 저장소 install/SKILL.md를 고쳐 올린 뒤 **사용자가 Claude 설정에서 재업로드**해야 반영.

[수정 회차에 적용할 것 — 진단이 아니라 다음 단계용. 보고서 끝에 그대로 옮겨 적어라]
- 저장소 파일에서만 고친다. 설치본을 직접 고치지 마라. 규칙 상수(ACCOUNTS_START 등) 값은 건드리지 않는다.
- 문구 교체는 지목된 곳이 아니라 파일 전체 grep으로 전부 찾아 고치고, 고친 뒤 같은 grep을 다시 돌려 확인(경고 목록은 SKILL.md 5단계·"문제가 생겼을 때"·주의사항 세 곳).
- 고친 뒤 파일을 다시 열어 눈으로 확인하고 나서 "완료"라고 말해라.
- 고친 뒤 실 CSV로 pipeline → build → detect_ended → tests를 다시 돌리고, 수정 전 산출 HTML의 임베드 DATA와 수정 후를 대조해 의도한 차이만 있는지 확인. index.html은 올리지 않는다(사용자가 다음 정상 실행 때 배포).
- 판정 조건을 바꿨으면 원래 잡히던 실패가 여전히 잡히는지 재확인(validate·validate_html 파괴 실험 재실행).
- "되돌리면 안 되는 것" 표를 건드렸으면 표도 갱신.
- 실측 출력은 마스킹 규칙대로. 기준선에 금액·잔고를 적지 마라.
- 수정과 검증은 다른 세션에서 한다.

[마무리 — 기준선 갱신]
1차 커밋(진단 직후, 보고 전): audit/last-audit.md만 push(). 2차 커밋(사용자 채택 뒤): audit/checklist.md(점검표 + 채택된 개정안, 머리말 버전 줄) + install/SKILL.md(부트스트랩 원본 — 사용자가 채택했을 때) + last-audit.md 정정분.
순서: ① push → ② codeload로 다시 받아 들어갔는지 확인(md5 대조, HEAD sha 확인) → ③ 그다음 채팅 보고. 보고를 먼저 길게 쓰지 마라.
진단 전문을 파일로도 내려줘(채팅 요약본 말고 파일). 토큰을 못 받았으면 push를 건너뛰되 파일을 반드시 내려주고 "저장소에 반영되지 않았다"고 명시해라.
보고 끝에 "내가 고를 항목"을 번호로 한 줄씩 정리해라(결함 n / 개선안 n / 점검표 개정안 n / 부트스트랩 재업로드 필요 여부). 나는 그 번호로 답한다. 내가 고르기 전엔 저장소 파일에 손대지 마라.
